01. Executive Overview

Krishna Sanjeevani is a therapeutic music streaming platform built on a Cloudflare-First Serverless architecture. This design handles millions of concurrent streams globally with sub-100ms response times, zero cold starts, zero egress fees (via R2), and auto-scaling logic.

02. System Context

The platform consists of three core components: React Web, React Native, and Hono Edge Workers. All components interface directly with Cloudflare's serverless primitives (D1, R2, Queues) at the nearest network boundary to optimize latency and scale linearly.

03. Architecture Overview

The backend utilizes a clean, layered boundary model: Route → Controller → Service → Repository → DB. This enforces separation of concerns, ensuring business logic changes do not affect database connection layers.

04. Application Architecture

05. Web Architecture

Built on React, Vite, and React Router. Uses a shared TypeScript API SDK to communicate with backend APIs. Client state is managed locally via React Context providers.

06. Mobile Architecture

Built on React Native and Expo Router. Implements custom native HLS streaming playback with offline caching capabilities to support network changes.

07. Admin Architecture

The Admin Console handles catalog CMS controls, pricing models configuration, subscriber details logs lookup, and infrastructure connectivity telemetry pings.

08. Backend Architecture

Hono-powered backend located in backend/src/. Structured by functional features: auth, tracks, programs, favorites, progress, subscriptions, storage, and stream.

09. API Architecture

RESTful API versioned under /api/v1/. The endpoints are protected based on roles, redirecting media session ticket requests dynamically.

10. Auth & Authorization

Stateless authentication using URL-safe signed JWT Access Tokens (15-min expiry) verified at the edge using Web Crypto APIs. Refresh Tokens (30-day expiry) are stored in D1 to manage session rotation.

11. Database Architecture

Cloudflare D1 SQLite database manages relational entities. Relational data is structured into normalized tables, while large binary objects are stored in R2 to avoid D1 capacity limits.

12. Database Schema

The database contains tables for users, profiles, tracks, programs, subscriptions, history, and analytics. Refer to the Database Schema Page for table fields and index definitions.

13. Content & Media

The ingestion pipeline decouples file uploads from transcoding. The upload API stores the raw MP3 to R2 and publishes a task to Cloudflare Queues immediately, allowing the media segmenter to process HLS segments asynchronously.

14. R2 Storage

Files are stored inside a private bucket. Processed tracks are saved as HLS playlists (.m3u8) and segment files (.ts) to enable adaptive bitrate streaming.

15. HLS Streaming

Tracks are streamed securely via a Worker proxy. Playback requires a temporary 5-minute streaming session ticket. The Worker validates the ticket and fetches segment files from R2, preventing direct asset URL hotlinking.

16. Queue & Processing

Cloudflare Queues handles asynchronous audio processing. Ingested tracks publish tasks containing the raw R2 key. The consumer worker segments the audio files, generates the playlists, uploads them back to R2, and deletes the original MP3.

17. Subscription & Payments

Subscription access tiers are verified inside the database. The payment provider integration operates in mock mode for testing, but is ready to connect to Razorpay APIs in production.

18. Pregnancy Engine

Calculates the gestational week of the pregnancy based on the Expected Due Date (EDD) to serve tailored daily raga playback schedules.

19. Progress & Sync

Playback offsets and program completion percentages are saved in D1, allowing users to resume listening seamlessly across web and mobile.

20. Security Architecture

Zero-trust security model: Private R2 bucket, HLS segment encryption (AES-128), sliding window stream ticket session validations, and Hono role-based endpoint authorization guards.

21. Low-Level Design

Inspect core service execution maps

+ 
// AuthService.login Flow
1. Verify request email & get password hash from D1.
2. Compare input password with hash via bcrypt.
3. Generate 15-minute access token (signed with HS256 JWT).
4. Generate 30-day refresh token & save SHA-256 hash in D1.
5. Return tokens to client.

// StreamService.getTicket Flow
1. Verify user JWT token & check subscription status.
2. Generate secure ticket UUID.
3. Save ticket session in D1 stream_sessions table (expires in 5 mins).
4. Return ticket token to client.

29. System Scalability & Autoscaling Blueprint

Krishna Sanjeevani is built on a highly scalable architecture, using Cloudflare's serverless primitives to process and stream audio with high performance and low latency.

V8 Edge Autoscaling (Workers)

The Hono backend runs on V8 Isolates instead of standard containers (Docker/VMs). Computation scales globally from zero to hundreds of thousands of concurrent requests instantly with zero cold starts, routing all requests to the nearest edge location.

Read-Replicated Database Scaling (D1)

Cloudflare D1 scales SQL read queries globally by utilizing local SQLite read replicas at the edge. This design isolates heavy database writes to the primary database coordinator, maintaining low-latency lookup operations.

Cost-Efficient Object Streaming (R2)

Cloudflare R2 provides zero egress bandwidth costs. Splitting tracks into HLS segment chunks allows the player to fetch only what is needed, caching hot segments on Cloudflare's CDN to scale delivery.

Queue Load Buffering (Queues)

Asynchronous media ingestion protects workers from gateway timeouts during high-traffic upload surges. Tasks are buffered in Cloudflare Queues and processed asynchronously.

Stateless Authentication (JWT)

Web Crypto APIs validate user JWT tokens locally at the edge worker, eliminating database roundtrips for standard request authorization checks and scaling auth checks linearly.

High-Concurrence Caching

Dividing audio into 6-second segments matches CDN caching parameters, serving repeat segment requests directly from the edge cache to minimize bucket operations costs.
